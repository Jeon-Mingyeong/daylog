- 배포 URL: `https://jeon-mingyeong.github.io/daylog/`

## 1. 개요

데이로그는 하루 동안의 식사, 수면, 기분, 건강 상태, 소비 내역을 한 기록에 통합하고 생활 패턴과 충동 구매 위험을 분석하는 개인 생활 기록 PWA이다.

### 1.1 목표

- 식사, 수면, 기분, 건강 상태를 기록한다.
- 소비 항목, 금액, 카테고리, 구매 목적, 필요한 소비 여부를 기록한다.
- 생활 기록과 소비 기록을 연결해 단순 집계 및 개인 패턴을 제공한다.
- 충분한 개인 데이터가 쌓이면 Logistic Regression 기반 충동 구매 예측 모델을 학습한다.
- API가 없거나 연결되지 않은 환경에서도 브라우저 로컬 기록 기능을 유지한다.

## 2. 사용자 기능 명세

### 2.1 화면 구조

앱 상단에는 앱 이름 `데이로그`와 사용자 표시 버튼이 있으며 하단 본문 위에 다음 탭을 제공한다.

1. 오늘 기록
2. 기록
3. 분석

데스크톱에서는 최대 760px 너비의 중앙 패널로 표시되고, 600px 이하 화면에서는 소비 입력·기록 카드·통계 카드가 모바일 레이아웃으로 변경된다.

### 2.2 오늘 기록

#### FR-01 날짜 선택

- 날짜 입력 방식: HTML `date`
- 기본값: 앱이 실행된 현재 UTC 날짜를 `YYYY-MM-DD`로 변환한 값
- 저장 형식: ISO 형식 날짜 문자열

#### FR-02 식사 기록

- 입력 항목: 오늘 먹은 음식
- 필수 입력
- 플레이스홀더: `예: 귀리 스무디, 닭가슴살 샐러드`
- 공백만 입력한 경우 저장하지 않는다.
- 자유 입력 문자열로 저장한다.

#### FR-03 수면 기록

- 취침 시간과 기상 시간을 HTML `time` 입력으로 받는다.
- 기본 취침 시간: `23:00`
- 기본 기상 시간: `07:00`
- 수면 시간 계산은 취침·기상 시각의 분 차이를 사용한다.
- 기상 시간이 취침 시간보다 빠르면 다음 날 기상으로 간주해 24시간을 더한다.

예:

```text
23:00 → 07:00 = 8시간
00:30 → 07:45 = 7시간 15분
```

#### FR-04 기분 기록

다음 다섯 가지 상태 중 하나를 선택한다.

| 기분 | 아이콘 |
|---|---|
| 아주 좋음 | ☀️ |
| 좋음 | 😊 |
| 보통 | 😐 |
| 불안함 | 😟 |
| 나쁨 | 😔 |

- 기본값: `좋음`

#### FR-05 건강 상태 기록

- 1~10 범위의 숫자 슬라이더
- 기본값: `7`
- 화면에 현재 값 `/10` 형식으로 표시한다.

#### FR-06 소비 기록

기본적으로 소비 입력은 비활성화되어 있으며 스위치를 켜야 표시된다.

지원 항목:

| 항목 | 입력 형식 | 기본값 |
|---|---|---|
| 항목 | 텍스트 | 없음 |
| 금액 | 0 이상 숫자 | `0` |
| 카테고리 | 선택 | `식비` |
| 구매 목적 | 텍스트 | 없음 |
| 소비 유형 | 필요한 소비 또는 충동 구매 | 필요한 소비 |

카테고리:

- 식비
- 쇼핑
- 교통
- 문화
- 생활
- 기타

항목이 비어 있으면 소비 데이터는 저장하지 않는다.

#### FR-07 메모

- 자유 형식 텍스트
- 필수 입력이 아니다.
- 오늘의 특별한 점이나 생각을 기록한다.

#### FR-08 기록 저장

저장 버튼 이름: `오늘 기록 저장하기`

저장 시 다음 동작을 수행한다.

1. 새 UUID를 생성해 기록 식별자로 사용한다.
2. 기록을 React 상태에 추가한다.
3. 기록을 `localStorage`에 저장한다.
4. `VITE_API_URL`이 설정되어 있으면 API에 기록을 동기화한다.
5. 소비가 있으면 충동 구매 예측 API를 호출한다.
6. 성공 시 저장 완료 토스트를 2.2초간 표시한다.
7. 입력 필드를 초기화한다.

API 요청 실패는 로컬 기록 저장을 차단하지 않는다. 화면에 API 오류를 별도 표시한다.

### 2.3 기록 화면

#### FR-09 기록 목록

각 기록 카드에는 다음 정보를 표시한다.

- 날짜
- 식사
- 취침·기상 시간
- 기분
- 건강 점수
- 소비 카테고리, 항목, 금액
- 메모
- 삭제 버튼

기록이 없으면 다음 상태를 표시한다.

- 빈 상태 아이콘
- `아직 기록이 없어요`
- 기록 시작 안내
- `기록 시작하기` 버튼

#### FR-10 기록 삭제

- 각 기록 카드의 삭제 버튼을 누르면 해당 `id`의 기록을 제거한다.
- 삭제 후 `localStorage`에 반영한다.
- API 삭제 엔드포인트는 구현되어 있지 않아 서버 데이터는 별도로 삭제되지 않는다.

#### FR-11 데모 데이터 생성

`14일 데모 데이터 만들기` 버튼을 누르면 최근 14일치 데모 기록을 생성한다.

데모 데이터에는 다음 정보가 포함된다.

- 다양한 음식
- 취침·기상 시간
- 다섯 가지 기분 패턴
- 5~9 범위의 건강 점수
- 소비 항목, 금액, 카테고리, 구매 목적
- 필요한 소비와 충동 구매 분류
- 일부 메모

생성 시 기존 데모 데이터는 제거하고 새 데모 데이터를 추가한다. 일반 사용자 기록은 유지한다. 생성된 데모는 API에도 동기화된다.

데모 식별자:

```text
demo-{index}-{timestamp}
```

#### FR-12 데모 데이터 삭제

데모 데이터가 있으면 `데모 데이터 삭제` 버튼을 표시한다.

- `demo-`로 시작하는 기록만 제거한다.
- 일반 기록은 유지한다.
- 삭제 전 서버 API에도 삭제 요청을 보내지 않는다.

### 2.4 분석 화면

#### FR-13 기본 통계

기록 수에 관계없이 다음 통계를 표시한다.

| 지표 | 계산식 |
|---|---|
| 누적 기록 | 전체 기록 수 |
| 평균 건강 | 전체 기록 health 평균 |
| 기록된 소비 | 소비가 있는 모든 기록의 amount 합계 |

#### FR-14 패턴 통계

기록이 3일 이상일 때 추가로 다음 패턴을 표시한다.

| 지표 | 계산식 |
|---|---|
| 평균 수면 | 모든 수면 시간의 산술 평균 |
| 좋은 기분일 건강 | 기분이 `아주 좋음` 또는 `좋음`인 날의 건강 평균 |
| 다른 기분 건강 | 위에 해당하지 않는 날의 건강 평균 |
| 가장 큰 소비 카테고리 | 카테고리별 소비 금액 합계가 가장 큰 카테고리 |

기록이 3일 미만이면 다음 안내를 표시한다.

```text
분석의 정확도를 높이려면 최소 3일 이상의 기록이 필요합니다.
```

#### FR-15 충동 구매 분석

- 충동 구매 건수: `necessary === false`인 소비 기록 수
- 충동 구매 금액: 해당 기록들의 소비 금액 합계
- 충동 구매가 없으면 안내 문구만 표시한다.
- 가장 많이 소비된 카테고리를 함께 표시한다.

#### FR-16 개인 모델 학습

`개인 모델 학습하기` 버튼을 누르면 다음 절차를 수행한다.

1. 브라우저의 전체 기록을 API에 동기화한다.
2. `/api/train`을 호출한다.
3. 학습 성공 시 학습 기록 수와 추정 정확도를 표시한다.
4. 데이터 부족 시 서버 오류 정보를 화면에 표시한다.

API URL이 설정되지 않았으면 요청 함수는 `null`을 반환하고 학습 결과가 없는 상태가 될 수 있다.

## 3. 데이터 명세

### 3.1 브라우저 기록 데이터

브라우저 키:

```text
daylog.entries.v1
```

로컬 데이터 형식:

```typescript
type Spending = {
  item: string
  amount: number
  category: string
  purpose: string
  necessary: boolean
}

type Entry = {
  id: string
  date: string
  food: string
  sleepTime: string
  wakeTime: string
  mood: string
  health: number
  note: string
  spending: Spending | null
}
```

데모 표시 키:

```text
daylog.demo.v1
```

`localStorage` JSON 파싱 실패 시 빈 배열을 사용한다.

### 3.2 API Entry 스키마

프론트엔드의 `sleepTime`, `wakeTime` 필드는 API의 `sleepTime`, `wakeTime` 별칭으로 전달된다. FastAPI 모델은 내부적으로 snake_case를 사용한다.

```json
{
  "id": "string",
  "date": "YYYY-MM-DD",
  "food": "string",
  "sleepTime": "HH:MM",
  "wakeTime": "HH:MM",
  "mood": "좋음",
  "health": 7,
  "category": "식비",
  "amount": 12000,
  "necessary": true,
  "purpose": "점심 식사"
}
```

### 3.3 SQLite 테이블

테이블명: `entries`

```sql
CREATE TABLE IF NOT EXISTS entries (
  id TEXT PRIMARY KEY,
  date TEXT NOT NULL,
  food TEXT NOT NULL,
  sleep_time TEXT NOT NULL,
  wake_time TEXT NOT NULL,
  mood TEXT NOT NULL,
  health INTEGER NOT NULL,
  category TEXT,
  amount REAL NOT NULL DEFAULT 0,
  necessary INTEGER,
  purpose TEXT
);
```

필드 설명:

| 필드 | 설명 |
|---|---|
| id | 프런트엔드 UUID 또는 데모 식별자 |
| date | 기록 날짜 |
| food | 식사 기록 |
| sleep_time | 취침 시각 |
| wake_time | 기상 시각 |
| mood | 기분 |
| health | 건강 점수 1~10 |
| category | 소비 카테고리 |
| amount | 소비 금액 |
| necessary | 필요한 소비이면 1, 충동 구매이면 0, 소비 없으면 NULL |
| purpose | 구매 목적 |

## 4. FastAPI 명세

API 서버 버전: `0.1.0`

FastAPI 문서 경로는 `/docs`를 제공한다.

### 4.1 공통 응답

- 성공: `2xx`
- 입력 검증 실패: `422`
- 서버 내부 문제: FastAPI 기본 `500`
- API 기본 URL 미설정 시 프런트엔드 요청을 실행하지 않는다.

### 4.2 `GET /api/health`

서비스 상태를 확인한다.

응답 예:

```json
{
  "status": "ok",
  "model_available": false
}
```

### 4.3 `POST /api/entries`

기록을 SQLite에 추가하거나 같은 `id`가 있으면 교체한다.

요청 검증:

- `id`: 문자열
- `date`: 문자열
- `food`: 문자열
- `sleepTime`: 문자열
- `wakeTime`: 문자열
- `mood`: 문자열
- `health`: 1~10
- `amount`: 0 이상
- `necessary`: boolean 또는 null

응답:

```json
{
  "saved": true
}
```

### 4.4 `GET /api/entries`

SQLite에 저장된 모든 기록을 날짜 역순으로 조회한다.

응답 요소에는 SQLite 컬럼명인 `sleep_time`, `wake_time`, `necessary`를 사용한다.

### 4.5 `POST /api/train`

필요한 소비와 충동 구매 데이터로 개인 Logistic Regression 모델을 학습한다.

학습 조건:

- 전체 학습 행 10개 이상
- `necessary` 값이 있는 기록만 사용
- 충동 구매와 필요한 구매 라벨이 모두 존재해야 함
- 현재 UI 데모 구성에서는 각 분류를 충분히 포함해야 학습 가능
- API가 표시하는 문구상 각 분류 최소 5건 필요

요청 본문은 없다.

요청 성공 응답 예:

```json
{
  "trained": true,
  "training_rows": 14,
  "estimated_accuracy": 0.714
}
```

데이터 부족 시 HTTP `422`:

```json
{
  "detail": {
    "message": "충동 구매와 필요한 구매 데이터가 각각 최소 5건씩 필요합니다.",
    "training_rows": 4
  }
}
```

### 4.6 `POST /api/predict/impulse`

충동 구매 위험을 예측한다.

요청:

```json
{
  "mood": "불안함",
  "health": 3,
  "sleep_hours": 4.5,
  "category": "쇼핑",
  "amount": 78000
}
```

요청 검증:

- mood: `아주 좋음`, `좋음`, `보통`, `불안함`, `나쁨`
- health: 1~10
- sleep_hours: 0~24
- category: 문자열
- amount: 0 이상

응답 예:

```json
{
  "impulse_probability": 0.73,
  "level": "높음",
  "source": "personal_model",
  "suggestion": "구매 전 24시간을 두고 실제 필요성을 다시 확인하세요."
}
```

위험도 수준:

| 확률 | level |
|---|---|
| 0.70 이상 | 높음 |
| 0.40 이상 0.70 미만 | 주의 |
| 0.40 미만 | 낮음 |

## 5. 충동 구매 예측 명세

### 5.1 학습 전 규칙 기반 예측

개인 모델 파일이 없는 경우 다음 규칙을 사용한다.

| 조건 | 확률 가중치 |
|---|---|
| 기본값 | 0.20 |
| 건강 점수 4 이하 | +0.18 |
| 기분이 `불안함` 또는 `나쁨` | +0.16 |
| 수면 시간 6시간 미만 | +0.12 |
| 금액 5만원 이상 | +0.18 |
| 금액 5만원 미만 | +0 이상, 최대 0.12 |
| 카테고리가 쇼핑 | +0.10 |

최종 확률은 최대 `0.95`로 제한한다.

### 5.2 개인 Logistic Regression

학습 특징:

- mood
- health
- 수면 시간
- category
- amount

모델 처리:

- mood와 category: OneHotEncoder
- health, sleep_hours, amount: StandardScaler
- 분류기: LogisticRegression
- 최대 반복: 1000
- random state: 42

타깃 값:

```text
충동 구매 -> 1
필요한 소비 -> 0
```

모델 저장 위치 기본값:

```text
backend/impulse_model.joblib
```

`DAYLOG_DATA_DIR` 환경변수가 있으면 해당 디렉터리를 저장소로 사용한다.

추정 정확도는 학습 데이터 자체에 대해 `model.score()`를 계산한 결과이다. 별도 검증 데이터나 교차 검증을 사용하지 않는다.

## 10. 보안·개인정보·운영 제약사항

### 10.1 현재 제한사항

- 사용자 인증이 없다.
- 서버 API에도 사용자 식별자가 없다.
- 모든 사용자의 기록이 하나의 SQLite 테이블에 저장될 수 있다.
- 개인 모델 파일이 서버 단일 모델로 사용된다.
- 브라우저 기록은 장치와 origin마다 별도의 localStorage에 저장된다.
- API 데이터는 CORS로 인한 브라우저 접근 제한만 있고 역할 기반 접근 제어가 없다.
- 음식, 기분, 건강, 메모, 소비 목적 같은 민감한 생활 데이터를 포함한다.
- Render 무료 플랜의 기본 파일 시스템은 영구 저장소가 아니다.
- 추정 정확도는 별도 검증 세트 없이 학습 데이터 자체의 점수이다.
- API 삭제 기능이 없다.
- 계정 삭제·데이터 내보내기·데이터 수정 API가 없다.
- 소비 내역 자동 연동이나 금융기관 API 연동은 없다.

### 10.2 현재 표시되는 개인정보 문구와 실제 동작의 관계

기록은 기본적으로 브라우저에 저장된다. `VITE_API_URL`이 설정된 경우:

- 새 기록 저장 시 API로 동기화된다.
- 데모 데이터 생성 시 API로 동기화된다.
- 개인 모델 학습 시 전체 현재 브라우저 기록을 API로 재동기화한다.

따라서 브라우저에만 저장된다는 의미는 API URL이 설정되기 전, 또는 API 호출이 실패한 환경에서만 완전히 적용된다.

### 11.1 사용성

- 모바일 화면을 우선으로 한다.
- 주요 입력은 카드 단위로 분리한다.
- API 실패 시 로컬 저장 기능을 유지한다.
- 저장 완료를 토스트로 알린다.

- 기록 상세: 2열에서 1열
- 통계 카드: 3열에서 2열

### 11.3 복원력

- localStorage JSON 파싱 실패 시 빈 기록 배열을 사용한다.
- API가 없는 경우 fetch를 호출하지 않는다.
- API 요청 실패 시 일반 기록 저장을 유지한다.
- FastAPI 시작 시 SQLite 테이블을 생성한다.
- 초기 예측은 모델 파일이 없어도 규칙 기반 결과를 반환한다.

- 인증과 사용자 식별자 추가
- 사용자별 데이터베이스 키 또는 테이블 스키마 추가
- 사용자별 모델 파일 분리
- SQLite에서 PostgreSQL 또는 다른 영구 데이터베이스로 이전
- 교차 검증과 시간 순 분할 검증
- 시계열 특징과 모델 추가
- 금융 소비 내역 연동
